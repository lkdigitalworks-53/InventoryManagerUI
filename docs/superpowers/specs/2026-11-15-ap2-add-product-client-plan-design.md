## 3. Decisions (all vetoable in the PR)
**D-AP2-1: the add key reuses the restock nonce.** `addProductNonce` is a one-line alias of `restockNonce`; `restockKey` and `addProductKey` share one `_validNonce`. Alternative: rename to a neutral `operationNonce` (touches R4's callers and tests for a name). Rejected: no behaviour gain. The server enforces the `addProduct:` prefix, so a restock key can never start an add (K-5).
**D-AP2-2: refuse bad numbers, never clip them.** `build` refuses a negative or non-finite price, selling price, stock, min stock, unit cost, a tax outside 0..100 and a non-boolean `taxable` (reasons `bad-price`, `bad-tax`, `bad-stock`, `bad-cost`). Today's code accepts anything the dialog lets through. Trade-off: a planner stricter than the dialog turns a silent bad doc into a visible refusal (and closes KNOWN-ISSUES 34 for this path: a non-numeric stock can no longer reach the server). Cost: AP3 must check that the dialog cannot produce a value the planner refuses (checklist in section 6). Cosmetic text is cut, never refused (feed title 150, SKU 100), like restock.
**D-AP2-3: `now` must be a real ISO instant, `date` a real day.** Stricter than RestockPlan (which only checks non-empty). Found by the monkey test M-1: `now: "{{{"` reached four stored docs. `now` is stored in the batch, the supplier and the `created` row, so it must be a timestamp. The same hole exists in RestockPlan (KNOWN-ISSUES 43, not fixed here). PR #201 sweep F1: the first version checked the SHAPE only, so `2026-13-45T25:61:61Z`, `24:00` and 31 February passed; the check now also needs `Date.parse` to succeed and the value to round-trip to the same second (`_realTime`), so it does not depend on how lenient an engine's parser is. `date` is checked the same way and need not agree with `now` (a local date near midnight differs from the UTC day).
**D-AP2-4: a known supplier id holding `{{` or `}}` is refused (`bad-supplier`)**, not neutralised. An id comes from the supplier store; one with a brace pair is no id, and neutralising would store a reference to nothing.
**D-AP2-5: every typed string is trimmed, then neutralised** (name, SKU, category, unit, size, description, new supplier name). The contract (section 9) named neutralising; trimming is added because the ledger already trims the product name (`cleanProductName`) and a trailing space in a stored name is never wanted. Cost: a stored name may differ from what the dialog showed by edge whitespace. AP3 verifies what the dialog already trims.
**D-AP2-6: `neutralisePlaceholders` uses a lookahead, not split/join.** `"{{{".split("{{").join("{ {")` leaves a `{{`; the lookahead gives `{ { {`. The contract example (`{{` -> `{ {`) holds; triples and longer runs also end with no pair (N-1).
**D-AP2-7: the `created` row stores the exact stock.** The legacy row used `parseInt(stock)` (2.5 shown as 2 in History while the product and batch hold 2.5). Fixed for the new path; the legacy path disappears in AP3.
**D-AP2-8: `reflect` requires exactly one feed row and one `created` row** (no legacy fallback, AP1 D-AP-10: an old build never sends `addProduct`). It reads only the results, so it works after a relaunch, and it checks every cross-doc fact: batch only when stock > 0, batch quantities equal the stock, the supplier doc exists exactly when its id was minted and the product and batch carry it, both history ids start with the product id and carry the SAME nonce.
**D-AP2-9: `FailureCause.forAddProduct`.** `conflict`, `mint-exhausted`, `request-id-in-use` get person-facing texts that say nothing was added; `not-found`, `insufficient-quantity`, `operation-too-large` are app bugs for an add (it reads no record and consumes no stock). The drift test over the server's whole code list now covers the third function.
**D-AP2-10: no supplier name in the plan.** An early draft carried `supplierName` for the feed row; the add's feed row has never shown the supplier, so it was removed (ponytail).
**D-AP2-11: AP1's dormancy pin narrowed, not deleted.** `operationLogic.addProduct.test.js` G-1 now skips `qml/helper/` (the planner and the label name the op type by design). `addProductPlan.test.js` G-1 guards that nothing outside the helpers refers to the planner or its keys. AP3 deletes both.

## 4. What the tests prove (details: test plan)
The plan runs through the REAL `validateOperationRequest` and `applyOperation` on the strict fake DB for every combination of supplier (none, known, new) and stock (0, fractional, whole); `reflect` reads the live and the replayed answer to the same value; AP1's K-2 dead end (a re-issued product number against surviving history rows) no longer happens because the ids carry the nonce; typed `{{prd}}`, `{{$stock}}`, `}}{{` are stored with one space and never as an id, a token or a 400. A seeded monkey sends 3000 random inputs (never throws, every accepted plan passes the real validator, no stray brace pair) and 3000 damaged answers to `reflect`.

## 5. Deploy and compatibility
Client helpers only; nothing loads them, so no behaviour changes and no deploy is needed (the server half is already live after #199). A revert is safe.

## 6. For AP3 (checklist, found while building AP2)
- The dialog must not be able to produce a value the planner refuses: negative or non-numeric price, stock, min stock, cost; tax outside 0..100; empty name after trim. Show the dialog's own message before the tap; map the planner's reason only as a backstop.
- Pass `now = new Date().toISOString()` and `date` from the same `Date` (R4 O4 pattern).
- Resolve `unitCost` (default = price, as `addProduct` did) and `sellingPrice` (default = price) BEFORE calling `build`.
- Decide with the dialog what trims today (D-AP2-5) so the stored text equals the shown text.
- Delete the two dormancy guards (AP1 G-1, AP2 G-1) in the same diff that wires the client.
- Photo: from the live answer only (D-AP-8). Offline: refuse with a clear text (D-AP-7).
- `reflect` can return `malformed-results` AFTER the server has committed (a live answer or a replay that fails one cross-doc check), and `forAddProduct`'s texts say "Nothing was added" only for REJECTIONS. Decide with Taher what the dialog does then. Recommended: treat it as "committed but unreadable": refresh the product list from the server and do not offer a plain retry, because a new tap makes a new key and a second product. Do not make `reflect` stricter to be safe: every extra check is one more way to refuse an answer that is already committed (PR #201 sweep, KNOWN-ISSUES 46a).
