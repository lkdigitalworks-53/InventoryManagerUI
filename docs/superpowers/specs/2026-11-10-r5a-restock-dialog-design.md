# R5a: the restock dialog's new supplier joins the operation, field limits, wording

Date: 2026-11-10. Branch `feat/2026-11-10-r5a-restock-dialog-supplier-in-op`. Parents: `2026-10-16-restock-atomic-operation-design.md` (architecture), `2026-11-02-r4-restock-wire-design.md` (what R4 left for R5). Status doc: `docs/superpowers/ATOMIC-OPERATIONS-STATUS.md` sections 10 and 11. Client only: no server change, no deploy ordering.

## 1. Why R5 was split

R5 as written in the status doc has four parts: (A) the typed supplier name goes into the operation (observation P1), (B) field limits and wording (R3/R4 observations), (C) the `activity_log` entry inside the operation (Q-A3, needs a server entity, a rules check, an id parameter on `ActivityLog.record`), (D) removal of `TransactionStore.recordPurchase` (P2). One chat turn cannot carry all four at the quality bar, and C is a different kind of change: it alters the server contract that every client sends to, so it needs a server deploy before the client. A and B are client only.

**D-R5-1 Order: A and B now (R5a), C and D next (R5b).**
- For: A fixes a real data defect that exists in the app today (section 2). C protects one UX feed row against a crash window the stock and batch already survive (R4-D9). A and B need no deploy; C does.
- Against: the design you approved (Q-A3) lists the activity row as part of the operation, and R5a leaves it on the client for one more slice. Nothing gets worse than it is on `main`.
- Rejected: C first (higher blast radius, smallest benefit); everything in one PR (cannot be reviewed or device-tested as one step).

## 2. The defect this slice closes (P1)

The Restock sheet has an inline "add new party" row. Its "Save" button called `SupplierStore.addSupplier`, which mints a supplier number with a separate network call, creates the supplier with a separate write, and only then did the person tap Confirm. So: type a new name, Save, then cancel the sheet or have the restock refused (product deleted elsewhere, stuck write, rejected) and a supplier now exists that no batch refers to, and a number was burned. That is the exact class of bug the arc exists to remove (G2), left in the one consumer that already uses the operation.

## 3. What changes

1. **"Save" becomes "Use" and creates nothing.** The typed name is held in the dialog (`_newSupplierName`), the combo shows "New: <name>", and a hint says the supplier will be added when the restock is confirmed. Confirm sends `{ newName }` as the party; `RestockPlan` already puts `mint supplier`, `create supplier` and the batch in the same transaction (R3).
2. **A name that matches a known supplier (case-insensitive, trimmed) selects that supplier instead.** No second "Acme". The match is made again at the tap, against the list as it is then, so a supplier that arrived by sync while the sheet was open is still found.
3. **A structured party.** `RestockFlow.supplierFor` accepts `{ id }` and `{ newName }` besides the old strings. A `{ newName }` is always a NAME. The old string form reads a leading `SUP-` as an id, so a new supplier typed as "SUP-Foo" would have stored a supplier id that exists nowhere. The string form is unchanged for existing callers (`DataModel.onRestockProduct`, tests).
4. **Limits, in the dialog and again at the tap** (`RestockFlow.makeInput`): reason at most 500 characters, supplier name at most 100, unit cost at most 1,000,000,000.
5. **Texts** for the three new refusals, each naming its limit; the existing texts are unchanged. A `maximumLength` property on `AuthTextField` (it did not forward one).

## 7. Review sweep of PR #191 (same branch)

Decisions made in the sweep, all vetoable in the PR:
- **D-R5-8 One spelling of a supplier name.** `RestockFlow._cleanName` (NFC, zero-width characters removed, every whitespace run folded to one space, trimmed) is applied to the typed name AND to each known name before they are compared, and the cleaned name is what is stored. Trade-off: a name typed with two spaces is stored with one; two suppliers that differed only by an accent form or invisible characters now count as the same. Alternative not taken: compare only, store as typed (the list would show the odd spelling the person could not see).
- **D-R5-9 The known supplier wins over the length limit.** A known name matches at any length; the 100-character limit applies to a NEW name only. Otherwise an imported 150-character supplier could never be picked by name and a duplicate would be forced.
- **D-R5-10 A name typed but not sent with "Use" is refused at Confirm** (message, nothing sent). Alternatives not taken: use it silently (a half-typed name could create a supplier nobody meant), drop it silently (what the first version did, booking the restock with no supplier).
- **D-R5-11 `costFromText` accepts a plain decimal only** (optional sign, digits, optional fraction). Hex, binary, octal, exponent, separators are refused as bad-cost. A person who types "1e3" for 1000 is told the cost is not valid and types 1000. A negative zero is a plain zero.
- **D-R5-12 The purchase total is rounded to 2 places** in `RestockPlan` (the order totals already are). The unit cost is not rounded: a per-unit cost with more places is a real case (a bulk price). A total too large to multiply by 100 is kept whole.
- The stock line under the quantity reads the typed text through `qtyFromField`, and `openFor` moves the SpinBox value away and back so a typed-and-abandoned text is rewritten.
- **D-R5-13 (review pass 3) The joiners stay in a stored name.** D-R5-8 removed U+200B to U+200D. U+200C (zero-width non-joiner) and U+200D (zero-width joiner) are part of how Hindi, Malayalam, Persian and other scripts are spelled and drawn (a conjunct loses its shape without the joiner), and suppliers here are typed in those scripts. Now `_cleanName` removes only U+200B, U+2060 and U+FEFF; the joiners are left out of the MATCH key only (`_matchKey`), so "Ac" + joiner + "me" and "Acme" are one supplier and a name of only joiners is still blank. Trade-off: a name can now carry an invisible joiner that a Latin-script reader cannot see; matching ignores it, so it cannot cause a duplicate. Alternative not taken: strip them everywhere (what the first sweep did), which silently misspells Indic names. Vetoable.
- **D-R5-14 (review pass 3, Taher chose option A) A queued new supplier name is held.** `restock` refuses (before queueing, minting or remembering anything) when the new supplier name matches, by `_matchKey`, the name of a `create supplier` op inside a still-queued `restock` item. Alternatives not taken: (B) allow and accept duplicate suppliers (no merge screen exists); (C) let a later operation point at the first one's supplier by token (server change and new request shape, a slice of its own). Trade-off accepted: the 2nd to 5th product from a brand-new supplier waits for the first sync or goes without a supplier, and a parked restock keeps holding the name until retried or discarded. Known suppliers, other new names and no supplier are not held. Two phones offline (O1) is not solved by this.
- **Review pass 3 also:** the QML twin `tests/tst_RestockFlow.qml` did not compile in CI (`var long`, a reserved word in QML's JavaScript), so none of its tests ran; renamed, and `qmlReservedWords.guard.test.js` fails fast in the Node job. `tst_InventoryStore_movementKinds.qml` still expected the old "cut at 500" and is replaced by four tests (refused over 500, 500 whole, trimmed length, 501 refused).
