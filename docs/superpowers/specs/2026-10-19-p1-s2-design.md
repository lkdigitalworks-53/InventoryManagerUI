## 1. What the code says today (read 2026-10-19)

- **Direct mode** is only used by `Gateway.recordMutation`, `recordEdit`, `recordMutations` (`_writeDirect`, `_writeDirectBatch`). `recordDelta` and `recordOperation` already refuse it. Default is `"gateway"`. Only `tests/tst_Gateway.qml` forces `"direct"` (lines 62, 183, 553, 950, 1800), partly to keep tests off the network.
- **`runCutover`**: no caller outside `Gateway.qml` (`Main.qml` only calls `MigrationService`, a no-op). Server side: `functions/index.js` export, `lib/cutoverLogic.js`, tests in `index.handlers.remaining.test.js` and a cutover test file.
- **Rules**: `firestore.rules` fallback `match /{collection}/{docId}` lets any member create/update/delete every non-ledger collection, so `inventory` is writable from a client with a token. Grep found NO client code writing `inventory` outside the Gateway. Other direct writers (`activity_log`, `config/*`, `tenants`, `users`, `members`, `_migrations`) are not inventory and must keep working.
- **Stock-changing client paths** (all via `InventoryStore`, callers in `DataModel.qml`):
  - `restock()` -> `recordDelta +N` (RestockDialog, and DataModel:310). Server derives `adjustment` today. Should be `receipt`.
  - `deductStock()` -> `recordDelta -N` (DataModel:973 and :1384, imported-order completion and a rollback). Derives `adjustment`. The imported-order case should be `sale`.
  - `creditStockNoBatch()` -> `recordDelta +N` (DataModel:1060, 1181, 1354: returns, rollbacks). Derives `adjustment`. Returns should be `sales_return`.
  - Manual stock edit in the product form, create, bulk import: whole-record `recordMutation`. Derived (`adjustment` / `receipt`). Already complete, only coarse (R4).
  - `completeOrder` runs through `recordOperation` and already derives `sale`.
- **Gateway has no `movements` param yet.** `Gateway.recordDelta(entity, id, deltas, floors, clamps, cb)` -> `OutboxStore.enqueueDelta`.
- **Hidden trap (new):** `OutboxStore.enqueueDelta` COALESCES a held delta for the same product by SUMMING `deltas`, taking the latest `floors`/`clamps`. If kinds are added without touching it, two coalesced calls (restock +10, then a loss -3) would send `stock: +7` with one kind, or drop a kind. Server D3 needs `sum(movements.qty) == applied delta`. Coalescing must CONCATENATE `movements` (cap 50 on the server), and a call carrying `clamps` must not coalesce with explicit movements (server rejects clamp + explicit movements).

## 3. Decisions (Q1-Q3 settled 2026-10-19, Q4-Q5 open)

- **Q1** Build S2e (pickers) now, or wait for the CA to say which of the 56(2) columns need intent kinds? Proposal: wait. Derived `adjustment` is already complete and auditable; pickers built before the CA answers may be thrown away.
- **Q2** Which slice first? Proposal: S2b (pure server deletion, sandbox-testable, no dependency on the dev deploy).
- **Q3** Lock only `inventory`, or every Gateway-routed collection (`orders`, `staff`, `suppliers`, `removed_staff`)? Proposal: `inventory` only now (YAGNI, ledger driver), note the rest as a follow-up.
- **Q4** Returned goods that are damaged: `sales_return` vs `destroyed`. Needs a UI choice on the return flow. Part of S2e, not S2d.
- **Q5** `valueAtCost` for intent kinds is client-stated (R1). Accept for dev, revisit before prod?

## 4. Trade-offs of the proposal

- Splitting into five PRs costs more review rounds but each slice is small enough for one token budget and one hand-off. One big S2 PR would likely die mid-session.
- Deleting direct mode before S2d removes the "flag flip skips the ledger" hole early, but forces test rewrites with CI as the only oracle.
- Locking rules (S2c) makes any old dev build still on direct writes fail with permission-denied. Dev-only per D10, so accepted.
- Skipping S2e leaves manual edits as `adjustment` (R4) until the CA answers.
