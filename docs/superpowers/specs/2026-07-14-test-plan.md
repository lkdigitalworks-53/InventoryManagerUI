# Test plan — fix/order-import-stock-and-holistic-bugs

**Covers:** all commits on this branch — the import order stock-check rewrite, productId-only
order-line matching, atomic id minting across Products/Orders/Staff/Suppliers (including the
bulk-import batch-mint path), their integration with the P0 Gateway migration + the restock
reason field already on `main`, and a second round fixing an on-device bug report: two rows in
one import file resolving to the same product or the same order+product with conflicting
details (price/stock/tax/discount). That second round also restores two files
(`DataModel.qml`'s `_findLine`/`_resolveInventory`, `InventoryStore.qml`'s `findByName`) that had
regressed back to name-based matching during the branch rebuild — caught while investigating the
duplicate-row report, unrelated to it but real.

**Read this first:** the id-minting algorithm (`FirebaseService.mintCounterValue`/
`mintCounterBatch`) was already tested and confirmed working against real Firestore. Everything
built *around* it in the rebuild — the `Gateway.recordMutation`/`recordMutations` calls, the
`reason`+`callback` merge in `restock()`, the batch-aware bulk-import path — has only been
verified by static tracing and mocked-network Node scripts, never against a live backend or a
running app. Section 3 (on-device) is where that gap actually closes. Prioritize it.

## 1. Unit tests

### 1.1 Already covered (automated, in `tests/`)
`tests/tst_ImportMath.qml` — 28 cases across two rounds:

Round 1 (14 cases, the import stock-check rewrite):
- `findOrderLineByProductId`: match at index 0, match past index 0 (the exact regression the
  original `break`-outside-`if` bug caused), no match, null/empty `products` array.
- `checkOrderLineStock`: not-completing always passes through; new line sufficient/exact/
  insufficient stock; existing line increase that fits/doesn't fit (clamps + issue); existing
  line decrease/unchanged never checks stock.

Round 2 (14 cases, fixing an on-device bug report — two file rows resolving to the same product
or the same order+product with conflicting details):
- `findDuplicateProductRows`: no duplicates is a no-op; blank Product IDs are never grouped with
  each other; identical duplicate rows keep the first and drop the rest (2-row and 3-row cases);
  conflicting price/stock is reported as a conflict, not silently overwritten or dropped.
- `mergeOrderLines`: no duplicates passes through unchanged; same-price duplicate lines merge by
  summing quantity (2-line and 3-line cases); different price/tax/discount is reported as a
  conflict rather than guessed; line order is preserved for the non-duplicate lines around a
  merged pair.

Run: `qmltestrunner -input tests/tst_ImportMath.qml` (or via whatever CTest target wraps it in
this project's build).

### 1.2 Gap — not covered by any committed test, recommend closing before/soon after this merges
- **`FirebaseService.mintCounterValue` / `mintCounterBatch`** have zero `qmltestrunner` coverage.
  During development these were verified with throwaway Node scripts that mocked `_request` —
  useful for catching control-flow bugs (and did catch a couple), but not part of the repo's
  test suite and don't touch real Firestore semantics. Recommend a `tst_FirebaseService.qml`
  with a stubbed network layer covering: first mint on a tenant with no counter doc (both
  `mintCounterValue` and `mintCounterBatch`), mint with a non-zero seed, sequential mints
  advancing correctly, a simulated precondition conflict (concurrent writer) triggering a retry
  that lands on the right value, exhausting the retry cap cleanly, and `count: 0` batch calls
  never touching the network.
- No existing tests for `OrdersStore`/`StaffStore`/`SupplierStore`/`InventoryStore`'s add/upsert
  functions at all (true before this branch too — not a new regression, but this branch made
  those functions meaningfully more complex, which raises the cost of that gap).

### 3.3 Edge cases — these map directly to the bugs this branch fixes, don't skip them

| # | Scenario | Expect |
|---|---|---|
| E1 | **The core bug.** Note the current highest product id (say `PRD-042`). Delete that product. Add a new product. | New product gets `PRD-043` (or higher) — **never** `PRD-042` again. Repeat for Orders/Staff/Suppliers with their respective prefixes. This is the single most important test in this whole plan. |
| E2 | **Concurrent add.** Two devices (or two logged-in sessions) tap "Add Product" within the same second, different product names. | Both succeed, each gets a **different** id, neither silently overwrites the other. Repeat for at least one other entity type if time allows (Staff or Suppliers). |
| E3 | **Fresh tenant, first-ever mint.** A brand-new company account with zero existing products. Add the first product. | Gets `PRD-001`, not a crash and not a collision — this exercises the "counter doc doesn't exist yet" precondition path specifically. |
| E4 | **Large bulk import with mixed new suppliers.** Import 50+ product rows, several referencing 3-4 distinct new supplier names. | Import completes in a reasonable time (not ~50 sequential network round-trips — that's the entire point of the batch-mint change); exactly as many new suppliers created as distinct new names; all ids sequential with no gaps or duplicates. |
| E5 | App backgrounded or killed (Android home button / force-stop) immediately after tapping Save, then reopened. | No duplicate record on reopen; either the operation completed or clearly didn't — no half-created state. |
| E6 | Add Staff with login enabled, but credential provisioning fails for an unrelated reason (e.g. email already in use). | The staff record itself was still created (id minted, doc written) even though login provisioning failed — confirm these two outcomes are properly decoupled, and the error shown is about the login step, not a generic failure. |
| E7 | Restock a product, `reason` field left empty. | Confirm this still works — `reason` is optional; don't let the new callback param silently require it. |
| E8 | **The reported bug, product side.** Import a file with 2 rows sharing the same Product ID but different prices (or stock, or any other field). | Neither row is silently applied — an issue is shown naming the Product ID and both row numbers; nothing gets imported for that id until the file is fixed. |
| E9 | **The reported bug, order side — the important one.** Import a file where one order has 2 rows for the same product at *different* selling prices. | The WHOLE order is rejected with a clear message (not partially imported, not silently picking one price). Then, separately: manually verify you can no longer reach the original "edit order, change second line's price, total gets corrupted" state through any import, since this is now the only path that could have produced it. |

### 3.4 Monkey testing
- Rapid multi-tap (3-5 taps in under a second) on the primary button of all 6 affected dialogs
  (Add Product, Restock, Add Staff, New Order, Add Supplier, Import's Apply) — confirm no
  duplicate records from any of them.
- Toggle airplane mode ON/OFF repeatedly (every 1-2 seconds) during a large bulk import — confirm
  it either completes cleanly or fails cleanly, no partial/corrupted state.
- Rapidly switch between screens / open a different dialog while an add is still in flight.
- Rotate the device (if the app supports it) mid-operation.
- Force-close and relaunch immediately after tapping Import on a large batch; check for
  duplicates or missing rows on relaunch.

## 4. Suggested order of attack
Given limited testing time, prioritize in this order:
1. **E1** (id reuse after delete) — this is the entire reason this branch exists.
2. **H1–H16** happy paths — confirms nothing is outright broken.
3. **N1–N9** negative paths — confirms the new failure modes (network round-trips that didn't
   exist before) degrade gracefully instead of hanging the UI.
4. **E3, E4** — fresh-tenant and large-bulk-import edge cases.
5. **E2** concurrent-add — needs two devices/sessions, schedule accordingly.
6. Regression checklist (Section 2) — spot-check rather than exhaustive if time is short.
7. Monkey testing last, time-permitting.
