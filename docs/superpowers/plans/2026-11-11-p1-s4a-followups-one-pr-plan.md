## Slice 2: D-R2, a `productName` snapshot in every ledger row (KNOWN-ISSUES 13)
**Why:** a deleted product shows only its id in the register (SR-D9). A CA cannot read that.
**Server:** `movementLogic.buildRows(movements, ctx)` gets an optional `ctx.productName`; write `productName` ONLY when it is a non-empty string (trim, cap 200 chars), else omit the field (never write `undefined`: Firestore rejects it). Four call sites pass it: `batchMutationLogic` (~l.157: `item.after.name` else `item.before.name`), `gatewayLogic` x2 (~l.237 mutation, ~l.309 delta: after-doc name else `current.name`; for delete use the BEFORE doc, the after is gone), `operationLogic` (~l.451: `a.after`/`a.before` name). Put the name picking in ONE pure function in `movementLogic` (`nameFor(before, after)`), not four copies.
**Register:** `stockRegisterMath` remembers, per product, the name of the LATEST row (by time) that carries one; `finish` uses `doc.name`, else that ledger name, else `null`. `deleted` stays `!doc`. Response shape unchanged (still `name`), so no client change. Old rows without the field are fine (dev only, no backfill, AGENTS rule 4).
**Tests:** `movementLogic` unit (name present, absent, blank, 300 chars, non-string, delete uses before); each of the four writers produces rows with the name (existing writer suites, one assertion each); register: deleted product gets its last ledger name, rename keeps latest, mixed old/new rows, all rows nameless gives `null`; SRG-06 field list gains `productName`; extend SR-27 (real `buildRows` into the register) so a created/renamed/deleted product keeps its name; monkey SR-28 oracle gains the name rule. Mutants: field not written in one writer, wrong row picked (first instead of latest), blank accepted.
**Test plan edit:** step 4 of the S4a plan (`name:null` for deleted product C) becomes "name is C's name".

## Slice 4 (droppable): D-R3, `count()` pre-check (KNOWN-ISSUES 14)
**Why:** a ledger over 250 000 rows answers 413 only after reading 250 000 docs, and every retry repeats it.
**Server:** before streaming, `const agg = await db.collection(path).count().get(); const n = agg.data().count;` (`firebase-admin` is `^12.6.0`, supports it; about 1 read per 1000 index entries). `n > REGISTER_MAX_LEDGER_ROWS` -> 413 `ledger-too-large` with zero document reads. Keep the in-stream cap as the backstop (rows can arrive between the count and the scan). A `count()` failure must NOT fail the request: log and fall through to the stream.
**Harness:** `handlerHarness.js` collection mock needs `.count()` returning `{ get: async () => ({ data: () => ({ count }) }) }` (record in `collectionGetCalls`-like field so a test can assert "zero ledger page reads").
**Tests:** over-cap = 413 and no page read; exactly cap passes the pre-check; `count()` throws = request still served; count says small but stream finds more = 413 from the backstop; guard test pins both caps. Mutants: pre-check removed, throw not caught, `>` to `>=`.
